# 開発工程・Codex使用量最適化

## 1. 基本原則

- 仕様判断、UI設計、受入条件はCodexへ考えさせず、この文書群を正本とする。
- Codexは1つのPhaseを1回の主要依頼で実装する。
- PhaseごとにGitHubへ明確なPRまたはコミット範囲を作る。
- ChatGPTが差分レビューし、修正指摘を重要度別に1回へ集約する。
- Codexの全面セルフレビュー、毎回のFresh Clone、毎回の実サーバーE2Eは行わない。
- バランス値は管理画面設定にし、数値調整のたびにCodexへ修正依頼しない。

## 2. Phase一覧

| Phase | 完成物 | Codex主要依頼目安 |
|---|---|---:|
| 1 | Paper基盤、Domain状態機械、永続化、管理画面骨格 | 1回＋集約修正 |
| 2 | 管理ホーム、オンライン参加者、ホワイトリスト管理 | 1回＋集約修正 |
| 3 | マップZIP、検証、複製、セットアップ登録、回収 | 1回＋集約修正 |
| 4 | 参加、準備、PvE、ファーム、コア、死亡復帰、クリア | 1回＋集約修正 |
| 5 | 妨害、全GUI統合、履歴、診断、ワンクリック運用 | 1回＋集約修正 |
| 6 | 実マップ統合試験、バランス初期調整、v1リリース | 原則修正1回 |
| 7 | YouTube入力アダプター | v1後に別計画 |

目標はYouTube前を主要4依頼＋統合修正で進める。重大な設計不整合がない限りPhaseを細切れにしない。

## 3. Phase 1：基盤

### 実装

- Gradle/Paperプロジェクト
- Domainの状態遷移とモデル
- Application Serviceインターフェース
- Repositoryインターフェースと安全なローカル保存
- 組込みHTTP、認証、共通API応答
- 日本語管理画面のナビゲーションとダッシュボード骨格
- サーバー状態・オンラインプレイヤーの読取り
- 操作ログ、operationId、診断基盤
- CIのビルド・単体テスト

### 対象外

- ワールドZIP、実ゲーム、Entity、YouTube、ランチャー

### 節目テスト

- 状態遷移単体テスト
- 設定の保存・破損・バックアップテスト
- API認証・入力・競合テスト
- Gradle build

## 4. Phase 2：管理ホーム・参加管理

- オンラインプレイヤー表示
- ホワイトリスト状態・一覧・追加・削除
- 日常運用向けホーム画面

## 5. Phase 3：マップ

### 実装

- ZIPアップロード、検証、安全展開
- MapProfile
- 原本保管、一時コピー、ロード、アンロード、所有確認削除
- ランダム選択・直前回避・次回固定
- MAP_SETUP状態
- 管理画面起点の地点・範囲クリック登録
- 必須項目検証
- 異常終了後の一時ワールド回収

### 対象外

- 敵、コア、ショップ、ゲーム進行の実動作

### 節目テスト

- Zip Slip、巨大展開、入れ子ZIP、破損ZIP
- 削除境界・所有確認
- マップ抽選
- セットアップ状態と保存/破棄
- 実Paperで小さなテストワールドの1回E2E

## 6. Phase 4：ゲーム本体

### 実装

- 管理画面Participant選択（参加ブロック/Zoneは将来候補）
- ゲーム開始時Inventory初期化、終了時ゲーム中Inventory削除
- PREPARING/ACTIVE/CLEAR/RECOVERING
- ファーム安全化、初期装備、資源再生成、ショップ
- 敵ゾーン、人数補正、所有敵
- 設定された必要通常Core数、最終ゲート、最終Core
- Boss Bar、Title、Action Bar
- Inventory維持での死亡復帰、再接続（Checkpointは将来候補）
- クリア・中止の共通Recovery

### 対象外

- 妨害、YouTube、最終ランチャー

### 節目テスト

- 1～4人倍率と抽選
- コアダメージ/破壊/ゲート条件
- 死亡・切断・オフライン終了者復元
- セッション所有物だけを削除
- 1ゲーム通しE2E

## 7. Phase 5：管理運用完成

### 実装

- 妨害4種と管理画面手動発動
- 全設定画面
- 装備・ショップ編集
- 履歴・ログ・診断・安全回収
- 管理画面から安全停止
- Windowsのワンクリック起動、二重起動防止、ブラウザ自動表示
- ユーザー向けREADME
- 開発コマンドを通常運用から非表示化

### 対象外

- YouTubeと外部公開

### 節目テスト

- GUIだけで初期設定からゲーム終了まで到達
- 妨害の対象外領域と連続受付
- 起動・停止・異常復旧
- v1全受入テスト

## 8. Phase 6：実マップ受入・v1

- ユーザー採用マップを管理画面で登録する。
- 1人、2人、4人想定でプレイする。
- コード不具合とバランス調整を分けて記録する。
- バランスは管理画面で調整し、コード修正を発生させない。
- コード不具合は再現手順をまとめ、1回の修正依頼に集約する。
- 合格後にv1タグを付ける。

## 9. Phase 7：YouTube入力アダプター

v1受入後に別計画で実装する。

## 10. GitHub運用

推奨ブランチ：

- `main`：受入済みのみ
- `phase/1-foundation`
- `phase/2-admin-home`
- `phase/3-map-management`
- `phase/4-gameplay`
- `phase/5-operations`

各Phaseの流れ：

1. ChatGPTが正式依頼書を作成。
2. Codexが対象ブランチで実装。
3. Codexが関連テスト→ビルドを実行。
4. CodexがPushし、定型報告を出す。
5. ChatGPTが仕様適合、重大不具合、回帰、テスト不足をレビュー。
6. 指摘をP0/P1/P2へまとめる。
7. P0/P1と受入必須P2だけを1回の修正依頼にする。
8. 再テスト後に人間がmainへマージする。

Codex自身へ別途一般レビューを依頼しない。GitHubの自動レビューを使用する場合も補助信号とし、ChatGPTの仕様レビューを置き換えない。

## 11. 各依頼書に必須の項目

- 目的
- 変更対象
- 明示的な対象外
- 参照文書と優先順位
- 実装要件
- 例外・安全要件
- 必須テスト
- 完了条件
- 報告形式
- Push/PRの可否

## 12. 使用量を増やすため避ける行為

- 仕様が曖昧な状態で全機能を一括依頼
- UI完成後にCoreを作り直す
- コマンド実装とGUI実装でゲームロジックを二重化
- 小さなレビュー指摘を都度Codexへ送る
- 数値調整をコード変更で行う
- Phaseごとの依存関係更新・全面整形
- 毎回の全テスト・サーバー長時間起動
- Codexへ仕様書を再解釈・再設計させる
